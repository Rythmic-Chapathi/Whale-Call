## 1. What you're building

A rideshare app for boats. Users book boat rides between tropical islands the way they
book an Uber between city addresses. There are two service tiers:

- **Standard rides** — normal point-to-point island hops. Browse, pick a boat class,
  price it, book it, track it.
- **Emergency rides** — urgent dispatch for people in trouble on the water: stranded
  vessel, medical evacuation, storm. Different fleet subset, different dispatch logic,
  different UI, no price shopping.

Emergency is a **first-class service type**, not a panic button. It has its own entry
point, its own flow, and its own boats. (There is *also* a separate in-trip safety
control — see section 8. Don't confuse the two.)

Aesthetic: tropical, illustrated, warm — a place you'd want to travel. Except in the
emergency flow, which strips all of that. See section 3.

## 3. Design system — two modes

The app has **two visual modes**. This is intentional and load-bearing. Do not blend
them into a single compromise style.

### Mode A — Voyage (default)

Everything except the emergency flow: landing page, browsing, fleet, standard booking,
trip tracking, profile.

- **Tropical palette** — turquoise and aqua water, warm sand, coral, sun-bleached
  wood, deep palm green. Warm, saturated, inviting.
- **Illustrated island map** — hand-drawn board-game adventure aesthetic. Stylized
  island shapes with visible coastline outlines, aged-paper texture on water and land,
  simple decorative terrain marks (palms, hills, small structures), hand-drawn line
  quality.
  - Reference for *feel only*: board-game adventure island map style. Build with
    original SVG shapes and CSS. Do not reproduce or trace any existing artwork.
  - Functional map first, decoration second. Boat icons and route lines must stay
    high-contrast against the styled background. If stylization hurts legibility,
    dial it back.
- Rounded, friendly UI. Generous whitespace. Soft shadows.

### Mode B — Response (emergency only)

Triggered when the user enters the emergency flow or an in-trip safety action fires.
The illustration falls away.

- High contrast. Near-black or deep navy background, one urgent accent color, white
  text.
- Map drops to a stark functional layer — land/water silhouettes only, no texture, no
  decorative marks. Position markers and heading are the only visual priority.
- Oversized touch targets. Large type. Minimum viable information per screen.
- No animations beyond essential state feedback. No decorative motion.
- Every non-essential UI element hidden.

**Why:** someone using this is stressed, outdoors, in bad light, possibly one-handed
on a wet phone. A charming treasure map is actively harmful there. The mode switch
should read as deliberate and reassuring, not as a different app.

Implement as a theme layer — token swap or context provider — so the transition is a
single state change, not duplicated component trees.

## 5. Data layer — fleet, drivers, islands

Build a seeded dataset and make it the **single source of truth**. This is the
foundation for everything else — do it before the map or the ride flows.

### Boats — 60 to 100

Each needs: id, name, class, capacity, current lat/lng, heading, status
(`available` / `en_route` / `on_trip` / `offline`), assigned driver id, home island,
and an `emergency_equipped` flag.

**Classes:**
- Water taxi — 1–4 passengers, cheapest, most numerous
- Cruiser — 4–8, mid tier
- Catamaran — 8–16, premium, island tours
- Speedboat — 1–4, fastest, priority pricing
- **Rescue** — emergency only. Never appears in standard booking. Medical/tow
  equipped. Should be roughly 8–12% of fleet, distributed so no island is far from one.

### Drivers — one per boat

id, name, avatar, rating, trips completed, years active, boat assignment, languages,
status synced to their boat. Rescue boat operators additionally have certifications
(medical, tow, night ops) shown in the emergency flow.

### Islands — 6 to 10

id, name, coastline polygon (for the illustrated map), dock/pickup points, whether it
has a rescue station.

### Rules

- Coordinates must sit on water, near islands and dock points. No boats on land.
- Realistic distribution — ratings cluster high with spread, classes weighted toward
  cheaper tiers.
- Enough boats that the fleet list needs pagination or filtering.
- **Consistency is the core requirement.** Boat #17 on the map, in the fleet list, in
  booking, and in trip detail is the same boat with the same driver, rating, and
  status. Delete every duplicated mock array you find and point that component here.
- Status propagates. Book a boat and it goes unavailable everywhere immediately.

**Done when:** you can pick a boat on the map, follow it through the full booking flow
into trip detail, and every field matches at every step.

## 7. Standard ride flow — model on Uber

Follow Uber's structure and interaction patterns closely. Don't clone their visual
design — our look, their proven flow.

1. **Set pickup + destination** — island/dock pickers, map selection
2. **Choose boat class** — stacked selector, ETA and price per class, Uber-style
3. **Confirm and request**
4. **Matching** — searching-for-boat state
5. **Driver assigned** — driver card (photo, name, rating, boat name/class), live boat
   position moving toward pickup
6. **Arriving / arrived** — see section 9
7. **In transit** — route line, live position, ETA to destination
8. **Complete** — trip summary, rate driver

Bottom-sheet pattern throughout, like Uber. Map stays visible, sheet carries state.
All data from section 5.

## 8. Emergency ride service

This is the differentiator. Build it as a real service, not a decoration.

### Entry points

- Prominent, permanently visible action on the landing page — distinct from the
  standard booking CTA, unmistakable
- Available from anywhere in the app via persistent affordance
- Available during an active standard trip (this is the in-trip safety control —
  it hands off into this same flow with trip context prefilled)

### Flow

1. **Situation type** — stranded/adrift, medical, taking on water, other. Large
   targets, minimum taps.
2. **Confirm** — single deliberate confirm step so it can't fire accidentally. Not a
   multi-screen form.
3. **Auto-locate** — pull current position, let user adjust on the stark map.
4. **Dispatch** — nearest available `emergency_equipped` boat, automatically. **No
   class selection, no price comparison, no bidding.** Speed overrides everything.
5. **Tracking** — Mode B UI. Assigned rescue boat, operator name and certifications,
   live position, ETA, distance. Persistent contact action.
6. **Resolution** — mark resolved, incident summary.

### Rules

- Switches to Mode B (section 3) on entry.
- If triggered mid-trip, carries context: current boat, driver, position, destination,
  ETA — the responder gets it, the user doesn't re-enter it.
- Rescue-class boats never surface in standard booking.
- Reachable in the fewest possible taps from any app state. Measure this and report
  the tap count.

## 9. Timer / ETA — build correctly

- Drive off a **target timestamp**, not a decrementing counter. Must survive
  re-renders, tab switches, and backgrounding without drift or reset.
- Clean up intervals on unmount. No leaked timers, no double-ticking on remount.
- Recompute ETA as boat position updates — don't count down blindly while the boat
  sits still.
- Format: minutes above 60s, "Arriving now" under threshold.

### Arrival — match Uber

Countdown doesn't hit zero and stall. It transitions:

- Countdown → "Arriving now" → "Your boat has arrived"
- Bottom sheet expands with driver details, boat identifier, contact actions
- Visual and haptic cue on arrival
- Wait timer starts
- Map recenters on pickup point

**Done when:** a full ride from request to arrival keeps accurate time throughout,
including across tab switches.
