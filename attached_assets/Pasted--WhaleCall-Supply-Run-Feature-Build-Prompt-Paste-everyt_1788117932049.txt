## 1. Feature overview

A user (signed in **or anonymous**, exactly like Response mode) can request supplies:

1. Choose **what they need** — icon-first categories, then quantities.
2. Choose **where it goes** — island + dock, or "my current location" via coordinates.
3. The system **automatically sources** the order from the nearest depot(s) that actually have the stock, **allocates a boat that can physically carry it**, computes a **priority score**, reserves inventory atomically, and creates a live-tracked delivery.
4. The user gets a tracking page reusing the existing trip-tracking UI, with live boat movement and a countdown.

The feature must integrate with — not sit beside — what already exists:
- A **Response mode** emergency can add supplies to the same dispatch (one boat, one run).
- Supply runs consume boats from the **same fleet pool** and show up on `/fleet`.
- Delivered runs appear in **Your logbook** (`/profile`) alongside crossings.

## 4. Priority scoring (pure, testable, explainable)

Put this in its own module (`server/supplyPriority.ts`) with **no I/O**, so it is unit-testable and so you can show judges the code.

```ts
const URGENCY_WEIGHT = { routine: 1, urgent: 3, critical: 5 };
const CRITICALITY_BONUS = { 1: 0, 2: 1, 3: 3 };   // highest-criticality line in the order
const ACCESSIBILITY_BONUS = 2;
const EMERGENCY_LINK_BONUS = 4;                    // attached to an active Response-mode dispatch
const DECAY_PER_MINUTE = 0.15;                     // unfilled orders get "louder" over time

function priorityScore(order, now) {
  const base =
      URGENCY_WEIGHT[order.urgency]
    + CRITICALITY_BONUS[maxCriticalityOf(order.lines)]
    + (order.accessibilityNeed ? ACCESSIBILITY_BONUS : 0)
    + (order.linkedEmergencyId ? EMERGENCY_LINK_BONUS : 0);
  const minutesWaiting = (now - new Date(order.createdAt)) / 60000;
  return +(base + minutesWaiting * DECAY_PER_MINUTE).toFixed(2);
}
```

**The time-decay term is required, not optional.** Without it a routine order can be starved forever by a stream of urgent ones. When a judge asks "what about fairness?", the decay is your answer: *unanswered requests get louder until someone responds.* Recompute scores on read, never freeze them at creation.

## 5. Sourcing + allocation engine (the core — make this bulletproof)

`server/supplyDispatch.ts`. This runs inside a single synchronous critical section so two concurrent orders can never claim the same last unit.

**Step 1 — Source the order.** For each requested line, rank depots by great-circle distance from the delivery position, and fill greedily from the nearest depot with `inventory[itemId] - reserved[itemId] >= needed`. If no single depot can fill a line, split it across depots. If the total available across all depots is short, fill what's possible and record the remainder in `unfilledLines`.

**Step 2 — Reserve atomically.** Increment `depot.reserved[itemId]` for every sourced unit **before** returning. Reservations convert to inventory decrements on `delivered`, and are released on `cancelled`. Never mutate `inventory` directly at order time — this is what prevents overselling.

**Step 3 — Allocate a boat**, with a fallback chain that must never dead-end:
1. `status === 'available'` **AND** `payloadKg >= totalWeightKg` **AND** (`refrigerated` if the order contains any cold-chain item) → pick the nearest to the first pickup depot.
2. If none: same filters but allow `status === 'en_route'` (it can be re-tasked), nearest first.
3. If still none **and** the order contains a criticality-3 item: allow a `rescue`-class boat to be re-tasked, and note this on the response as `"Re-tasked a rescue vessel for a life-critical run."`
4. If still none: **return a specific, actionable 409** — not a generic failure. See §6.

**Step 4 — Route + ETA.** Path is `boat.position → each depot in nearest-first order → destination`. Compute total great-circle distance; ETA at a per-class cruise speed (speedboat 45 km/h, water_taxi 32, catamaran 28, cruiser 25, rescue 40). Fare = `base 12 + 1.10/km + 0.35/kg`, rounded to 2 dp, with a **`priorityDiscount` of 100% applied to any order linked to an active emergency** — supplies attached to a rescue are free, and say so in the UI.

**Step 5 — Advance status on a timer.** A server interval (every 5s) walks active orders: `sourcing → allocated → loading` (after 30s) `→ in_transit` (after 60s) `→ delivered` (on ETA elapse). On `delivered`: decrement real inventory, release reservations, set the boat back to `available`, and set `deliveredAt`.

| `PATCH` | `/api/emergencies/:id/supplies` | Attach supply lines to an existing Response-mode dispatch |

### Error handling — fix the existing bug while you're here

The app currently swallows real API errors and shows generic "could not be reached" text, which made a working server look offline. **Do not repeat this.**

Every error response must be `{ error: string, code: string, remedy?: string }`, and **every** client-side catch must render `error` (falling back to a generic string *only* on an actual thrown fetch/network exception).

Required specific errors:
- `409 INSUFFICIENT_STOCK` — *"Only 3 of 8 water jugs are on the shelf right now."* + `remedy: "Reduce the quantity or send what's available now."`
- `409 NO_CAPABLE_BOAT` — *"No boat on the water can carry 620 kg right now."* + `remedy: "Split this into two runs, or reduce the order."`
- `409 NO_COLD_CHAIN_BOAT` — *"No refrigerated hold is free for the insulin cold pack."*
- `400 INVALID_DESTINATION` — destination dock doesn't belong to the destination island.
- `400 EXCEEDS_MAX_PER_ORDER` — names the item and its cap.

When stock is short, the API must **still offer the partial fill** in the response body (`{ canPartiallyFill: true, filledLines, unfilledLines }`) so the UI can say "Send 3 now, and we'll flag the rest" instead of dead-ending.

## 9. Tests (write these — they are also your proof to judges)

`server/__tests__/supply.test.ts`:

10. On `delivered`, inventory decrements exactly once and the boat returns to `available`.
